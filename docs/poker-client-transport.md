# Authoritative room transport and connection screen

This adds the first browser-to-owner transport. It uses same-origin HTTP POST and sequential one-second polling, **not WebSocket**. `/poker-demo` remains the approved local simulation and is unchanged. `/poker-online/<room UUID>` is a separate authenticated integration screen, not linked as a live lobby table yet. No guest authorization, room provisioning, production database change or Railway service is installed.

## Explicit server composition

A trusted Node 24 process must construct the existing `TournamentRoomRegistry` with dedicated service-role directory/store clients, encrypted checkpoint key ring and server clock. Create its player handler with the exact public website origin and Supabase **public** authentication key; pass that handler to `createPokerRoomHTTPServer`. Construction does not listen. The operator must explicitly bind the returned Node HTTP server, route every request for a room to this SAME process, start `RoomScheduler` for its registered rooms and close both on shutdown. The registry does not discover/provision rooms or recover halted owners automatically. See the prior registry and scheduler documents.

Set server-only Next environment `POKER_ROOM_SERVICE_ORIGIN` to the fixed service origin (no trailing slash, path, credentials or query). This is a server configuration, never a browser-supplied URL. Keep the internal service private behind the website gateway; HTTP on a trusted private network or TLS externally is required. Never expose database service credentials or checkpoint keys to Next client props or `NEXT_PUBLIC_*` variables. Without configuration the screen displays an unavailable notice, all connection buttons are disabled, and the API returns 503. This is the default for current Preview/production.

The Next gateway `/api/poker/rooms/<UUID>` requires same-origin POST and passes only Origin, Authorization, X-Poker-Connection and Content-Type to the fixed upstream; cookies and other headers are not forwarded. The player handler independently re-verifies the bearer with Supabase Auth and current suspension/admission for every operation. The browser session supplies a credential only. Both ingress layers bound body bytes at 4096, disable redirects/caching and have ten-second upstream/response limits. Node ingress bounds active handlers (default 32) and header bytes. A response timeout/abort does not undo an already-dispatched durable commit; the browser treats network/5xx/408/429 results as uncertain. This is not a per-user rate limiter or distributed owner election.

## Browser behavior

The connection capability is held only in memory. No URL, storage, analytics or rendered DOM receives it. Requests are serialized; polls cannot overwrite a later action with an earlier response. Each wager captures the current server hand/revision and a random action ID. Uncertain delivery retains the exact command, disables new wagers, and exposes a result-confirmation button that resubmits the same command/ID. A reconnect preserves that pending command. Definitive 4xx failures clear it; stale hand/token needs an explicit reconnect. Another tab cannot trigger a reconnect-stealing loop automatically.

Only server-projected board/own holes/public showdown holes, chip amounts, positions, legal actions and payouts are rendered. No client deal, chip mutation, winner calculation or authoritative timer exists. Final-level wording stays visible; a champion shows the exit link. Polling stops on errors and does not run while an action needs confirmation. Teardown or auth-account change clears private cards and prevents late responses from repopulating the old client. Reload loses an uncertain in-memory command, so the user must reconnect and inspect the current server state before acting; no browser command persistence is introduced.

The screen is a responsive integration table with navigation back to the site/lobby, not the finished demo layout/animation replacement. Seat requests still require backend assignment and current admission. The UI does not create a seat entitlement. The clock/turn authority remains server-side. Closing a tab does not send a reliable disconnect; presence leases/heartbeats and WebSocket push remain future work. This transport does not yet support leave controls, time-bank/AUTO actions, structure details, lobby entry/assignment or production startup discovery. A single process can run the separately composed scheduler; this change launches none.

## Verification

`npm run test:poker` includes actual loopback TCP HTTP + gateway + authenticated handler + durable owner tests: private projections, explicit reconnect token rotation, lost acknowledgements/503 exact retries, held durable writes, serialized state refresh, teardown, missing credentials, body/origin/route/config limits and concurrency saturation. React projection tests verify hidden cards, positions/final level and disabled unconfigured controls. CI also runs React effects/buttons lifecycle checks and the existing 169 isolated SQL checks. Test identities, keys and stores are local ephemeral fixtures; no production rows or real member credentials are used.

Manual live-room checks will only become possible once the backend is deliberately provisioned/configured. Then use two assigned test accounts in separate browsers: seat/connect, verify only own holes before showdown, act/check chip totals in both windows, reconnect one window and verify the old connection stops, complete the tournament and use the exit link. Network loss during an action must show result confirmation and block new bets. Current unconfigured Preview can verify only the unavailable notice/navigation, not real multiplayer play.
