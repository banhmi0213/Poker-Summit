# Assigned-room lobby and atomic join

This connects the authenticated lobby to rooms already assigned by the trusted backend. It is **not open tournament registration, payment, roster creation or automatic matchmaking**. The existing configured tournament/sample previews remain as demos. Signed-in users get a separate "your assigned tables" section; guests do not query assignments. Without the room-service configuration, it displays a preparation notice and sends no requests.

## Directory and API

The new prepared `20261017031737_poker_room_lobby.sql` adds a member-first admission index and `poker_room_assignments(p_member)`. This is a stable SECURITY INVOKER function with empty search_path and EXECUTE only for service_role, explicitly revoked from PUBLIC/anon/authenticated. It uses existing backend-owned admissions/bindings and returns only room/tournament UUIDs, title, frozen start, capacity and current published flag. Disabled rooms and deleted/revoked members are excluded. Unpublished rooms remain listed for existing-seat continuity. No rosters, member IDs, hole cards, checkpoint data or keys are returned. Up to 65 rows are read; the adapter accepts at most 64, rejects duplicate/invalid assignments and strips unexpected fields, so overflow fails closed instead of silently omitting a room. Pagination/archive policy remains future work.

`createPokerLobbyHandler` requires exact configured Origin, POST, JSON `{type:"assignments"}`, bounded bytes and a freshly verified bearer identity. No member/room/viewer override, query string, cookie-only auth or connection capability is accepted. The Supabase composition uses the same fresh Auth user and suspension verification as player requests. A dedicated backend directory client performs lookup for that verified UUID; this service-role RPC must never be exposed directly to the browser. Responses disable caching and contain no internal errors. Assignment listing does not load/create a room or reveal another member's table.

The explicit Node HTTP composition now accepts optional `lobbyHandler: registry.lobbyHandler({origins,auth})` alongside `registry.playerHandler(...)`. It shares the bounded ingress at `/api/poker/lobby`. The Next POST gateway forwards to that fixed upstream path via existing server-only POKER_ROOM_SERVICE_ORIGIN and strips unrelated headers/cookies. No upstream routing or member identity comes from browser input. Backend composition/configuration is still an operator step; this change starts no listener or scheduler.

The lobby client obtains a bearer credential, requests only its assignments, and links each result to `/poker-online/<UUID>`. It does not infer authority from JWT metadata or list data; the server checks admission AGAIN on join/state/action. User changes/sign-out clear the old list, and generation guards discard delayed prior-account responses. A reload control handles errors or assignment changes. Assignment links use ordinary navigation, not automatic seating/prefetch mutations. Published demo tournament cards still do not enroll users.

## Atomic join

The table's "join/connect/reconnect" button submits exactly `{type:"join"}`. No stack, seat, member or capability override is allowed. The handler first checks existing connect admission, separately derives current permission to create a new seat using the seat authorization rule, and passes only this trusted boolean to the durable owner. A false new-seat permission never prevents an already seated member from reconnecting.

Inside ONE owner FIFO transaction and ONE durable save, join reconnects the existing seat or selects the first vacant physical seat and connects it. Initial stack comes from frozen room policy. Concurrent members cannot take the same vacancy; repeated joins rotate the connection, never add another seat/chips. New seating is rejected after a hand exists, at a full table or when unpublished. Already seated participants can reconnect during play or after unpublishing without redealing, chip resets or altered deadlines. Unknown/unassigned/disabled members are denied by the existing directory authorization. The scheduler still requires the complete original roster connected before first deal. This is a fixed registered roster, not late entry/re-entry or table movement.

As with other mutations, no acknowledgement/private state escapes until save succeeds. A failed/ambiguous save halts the owner. Lost join acknowledgements can be retried safely as reconnects because a member has at most one seat. Pending betting receipts remain intact across explicit join/reconnect, using the existing action-ID confirmation mechanism. Join is not a browser-facing SQL function and adds no browser grants.

## Validation and deployment status

Node tests cover verified own assignments, strict request/adapter limits, current admission/publication, two/six concurrent auto-seats, one-save commit barriers, reconnect without new chips/deal, failure halt and real gateway/HTTP dispatch. React effect/button tests verify assigned links, nonpublic reconnect guidance, unavailable configuration, sign-out and delayed response removal. The isolated PostgreSQL admission suite now applies all four prepared backend migrations and checks actual assignment isolation, unpublishing/disable/deletion, index, fixed search_path, invoker rights and denied browser EXECUTE/RLS. No remote database is used.

Free pre-start intake is now prepared separately in [poker-tournament-registration.md](poker-tournament-registration.md); single-table manager configuration and registration-to-admission handoff are now prepared in [poker-registration-management.md](poker-registration-management.md). All SIX backend migrations remain UNAPPLIED to production. No Railway, service environment, room roster, production merge or live online play is enabled here. Live manual verification requires explicitly configured test infrastructure and two or six assigned test accounts. Later verify each sees only its table, follows the link, joins a unique seat, reconnects without stack reset and is denied after admission revocation. Open registration, admin assignment controls, startup discovery/recovery and final demo-layout integration remain separate development.
