## 3. デプロイの流れと落とし穴（重要）

1. PR を検証ブランチにマージ → Vercel が検証サイトを更新（数分）。
2. 同時に GitHub Actions「Poker engine tests」が push で走る（20〜30分）。
3. **Railway は「Wait for CI」がオンで、全部のテストが通らないと新版を入れない（落ちると SKIPPED）。**
4. **さらに Railway は、コミットした人が Railway のチームにいないため、毎回「承認待ち（PENDING）」で止まる。** オーナー（またはオーナーの依頼先）が Railway の Deployments で一番上の行の「Deploy」を押さないと切り替わらない。直すには Railway の「Invite them」でコミットしている GitHub アカウントをチームに入れてもらう（未対応）。
5. **データベースの関数（マイグレーション）は自動では入らない。** 検証 DB には MCP（apply_migration）で手で入れる。
6. **サーバーとデータベースの持ち時間を必ず揃える。** 持ち時間は `poker_private.ring_turn_interval()`（DB）と `RING_TURN_MS`（lib/poker/ring-play-runtime.ts）の両方にある。片方だけ変えると「画面は残り時間があるのに操作が弾かれる」状態になる（10/28 夜に実際に起きた）。新しいサーバーが ACTIVE になったのを確認してから DB を合わせる。
7. 新版が動いているかは、DB の記録（`poker_private.ring_hand_commits` の手と手の間隔）や Supabase の edge_logs（どこからの問い合わせか、1回の時間）で確かめる。

## 7. ローカルでテストを回す方法（新しいチャットでは作り直しが必要）

- テストは `node --test tests/poker-*.test.cjs`。依存（next / @supabase / ws / react の代わり）が無いと動かないテストがある。元のチャットでは作業場所に代わりの最小モジュール（`nm/`）を作り、`NODE_PATH` で渡していた。新しいチャットでは `npm install` するか同じように用意する。
- DB を使うテスト（`db/tests/poker_ring_*_isolated.cjs`）は CI では pglite（`POKER_PGLITE_MODULE`）を使う。手元で pglite が入れられない場合は、ローカルの PostgreSQL＋pglite 互換の薄い代わりで回せるが、配列パラメータで止まる箇所がある（そこまで進めば OK の目安）。**最終判断は CI（GitHub Actions）の結果で行う。**
- CI の失敗の中身はログ本体が取れない環境なので、check-run の annotations（`gh api repos/.../check-runs/<id>/annotations`）で見る。`tests/poker-ring-browser-e2e.cjs` は失敗時に `::error::` で画面の中身を出すようにしてある。
- 席を選ぶブラウザのテスト（Verify selected seats and per-hand timebank in browsers）は1手番の中で重い画面操作をするので、テストの中だけ持ち時間60秒（`ring_turn_interval` を差し替え、`turnMs:60000`）。それでもたまに `[data-board-count="3"]` 待ちで落ちることがある（落ちたら失敗ジョブだけ再実行。原因調査は未完）。
