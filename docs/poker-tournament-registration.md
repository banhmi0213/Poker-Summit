# Free pre-start tournament registration

This adds **free, pre-start intake**, cancellation and capacity accounting, separate from room admissions and starting stacks. It charges/transfers no money, wallet chips or prizes. It does not implement late registration, re-entry, waitlists, refunds or automatic matchmaking. A successful registration means "awaiting table assignment", not that a game/seat has started.

## Trusted configuration and SQL boundary

The fifth prepared backend migration `20261017032535_poker_tournament_registration.sql` creates private registration policies and entries. Policies have capacity 2–600 and an enabled flag; entries have a (tournament, member) primary key, Auth-user foreign key and server timestamp. Member-first indexing supports own-history lookup. Tables have RLS, no PUBLIC/anon/authenticated grants/policies, and limited service-role grants. There is no browser-facing SQL RPC permission or use of user_metadata.

A trusted operator/server can call `poker_registration_configure(tournament UUID, capacity, enabled)`. It locks the tournament row, validates capacity, rejects a capacity below existing registrations and refuses changes after start or any room binding. Initial policies are not automatically created/enabled. The admin configuration UI is NOT connected yet; no production policies are created here. Browser lobby requests cannot configure or override capacity/price/member/stack.

All four new functions are SECURITY INVOKER with empty search_path and service-role-only EXECUTE. Status/catalog expose only title, tournament UUID/start, capacity/count, own registered/assigned flags, registrationOpen and canCancel. Assigned means this specific member has an admission, not merely that some other members have rooms. No full entry list, member IDs, private cards/checkpoints or financial data crosses this boundary. Future published configured events and one's own registrations are listed, including own unpublished/started events for continuity. Catalog reads 65 rows; the adapter accepts at most 64 and fails closed on overflow/invalid/duplicate data. Pagination/history archiving remain follow-up work.

`poker_registration_change` accepts only register/cancel and a verified server member UUID. It locks the SAME tournament row used by configuration and room provisioning before counting/updating. The unique entry key prevents duplicate registrations; repeated requests for an already-present/absent desired state do not change the count. A full registration returns full without inserting. Cancellation before freezing releases one slot, including while intake is paused or the event is unpublished. Unknown/unpublished events disclose no state to nonregistrants. Current suspension/deletion is checked through existing Supabase request verification; Auth deletion cascades entries. After binding a room, a deleted participant does not become eligible for replacement/late seating automatically.

New entries require enabled + published, a real clock before starts_at and no existing room binding. Cancellation and policy edits also stop at start or any room binding. These checks use **clock_timestamp AFTER the row lock**, not transaction-start now(), so a request waiting across a deadline cannot add a late entry. Already-registered register retries can return current confirmation after freeze, without adding chips, seats or a second record. A retry is idempotent against the current membership state; it is not a journal of alternating register/cancel intents across multiple tabs. The UI sends no automatic mutation retries after an uncertain outcome.

## HTTP and browser

The existing bounded authenticated same-origin lobby endpoint gains strict `{type:"registrations"}`, `{type:"register",tournamentId}` and `{type:"cancel-registration",tournamentId}` commands. Identity comes only from fresh Auth verification, never a browser member field. Directory errors/invalid projections fail closed; full/closed return sanitized 409, unavailable returns 404. Cookie-only/cross-site/query/extra-field requests are rejected. Registry explicitly composes the registration directory with the lobby handler. No server is launched.

Signed-in lobby users see an additional free intake section when the service is configured. It displays actual confirmed counts, registered/waiting/own-assigned status and legal register/cancel controls. Each mutation is followed by a fresh catalog read, not an optimistic count change. Full/closed conflicts refresh status. Network/unknown results block further mutations until a successful reload. Single-flight UI controls suppress repeated clicks. Sign-out/account changes clear records and generation guards discard delayed catalog/action responses, including preventing an old-account acknowledgement from triggering another catalog request. Unconfigured/guest paths make no intake requests and offer no real entry actions. Existing sample/demo tournament cards remain demos, not enrollment.

## Registration-to-room handoff is next

Entries do NOT yet create admissions/rooms or auto-start the scheduler. The next step must freeze/validate the exact eligible registration roster, reconcile assigned members, persist/pristine-provision room(s), then expose their admissions to the existing assigned-table lobby. The existing trusted provision API can still operate independently; operators must not provision a partial intake roster and assume other registrants are assigned. Any binding intentionally freezes further intake to prevent roster drift, and each member's assignment flag remains false until their admission exists. Multi-table grouping/balancing and admin configuration/finalization controls remain future work. The existing engine cannot admit mid-hand/late-entry replacements.

## Verification and deployment status

Actual isolated PostgreSQL tests cover policy/capacity validation, duplicate registration/cancel, full rejection, released slots, pause/unpublication/start/assignment freezes, per-member assignment flags, deleted users, response privacy, real directory/HTTP composition, invoker/search_path/indexes and browser ACL/RLS. Concurrent JS requests on PGlite yield exactly the available slots, but PGlite uses one connection: **this is not a cross-session PostgreSQL lock stress test**. The row-lock design shares the provision/configure lock order; deployment QA should additionally test competing real database sessions and lock waits across the deadline.

Node regressions validate strict request grammar, verified identity, business-error mappings, missing configuration, adapter allowlists/bounds, RPC arguments and abort-before-dispatch. Real React effects/buttons exercise confirmed register/cancel counts, full conflicts, uncertain results/reload, cancellation locking, unavailable configuration and sign-out with late catalog/action responses.

All FIVE backend migrations remain UNAPPLIED to production. No real registrations, policies, production merge, service environment or Railway changes are made. Live manual verification requires deliberately configured backend/test tournaments; currently no user action is needed. After deployment of test infrastructure, check two accounts competing for the last slot, duplicate submit, cancellation/re-registration, deadline/finalization rejection and own-only assignment status. Railway remains deferred until development completion.
