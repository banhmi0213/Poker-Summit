# Optional WebSocket commit notifications and presence

This is an explicitly attached companion to the existing HTTP transport. It sends **only** `{type:"ready"|"changed",revision}`. Cards, chip projections, commands, member IDs and capabilities are never broadcast. The browser responds by requesting its own personalized snapshot through the existing serialized/authenticated HTTP client. The one-second HTTP check remains as a fallback for missed/coalesced notifications and clock updates. Betting commands stay on the idempotent HTTP path; WebSocket messages cannot deal, bet, reconnect, recover or administer a room.

## Explicit composition, no deployment

After creating the Node server, call `attachPokerRoomWebSocket(server, {origins, handler, owner})` using the SAME registry's player handler and owner lookup. `owner` must resolve to the same process-local owner used by HTTP and the scheduler. Construction attaches upgrade handling and starts an unref heartbeat, but does not listen. Explicitly await bridge.close(), close the scheduler and then close the HTTP server during shutdown. Imports start nothing. ws is a pinned direct dependency (8.22.0), @types/ws 8.18.1; the implementation follows ws's official noServer upgrade and ping/pong patterns, with compression disabled.

Configure server-only Next `POKER_ROOM_EVENTS_ORIGIN` to the public WebSocket origin (for example `wss://rooms.example.com`, no trailing slash/path/query/credentials). This origin is intentionally delivered as a client prop, so it must contain no secret. `/api/poker/rooms/<UUID>/events` must route to the room's Node process through a WebSocket-capable reverse proxy; the existing Vercel Next HTTP gateway does not proxy upgrades. Production requires WSS; the browser client allows plain WS only for loopback development. HTTP still uses the separate private `POKER_ROOM_SERVICE_ORIGIN` gateway configuration. With events configuration omitted, the existing HTTP-only integration screen behaves as before. No environment, server, domain, Railway service or production migration is provisioned by this change.

## Admission and delivery

The upgrade requires an exact configured website Origin and exact query-free event path. Cookies are ignored; Authorization headers/subprotocols are rejected, and no bearer/capability travels in a URL. Within five seconds, one bounded text frame must contain exactly `{type:"subscribe",token,connectionId}`. The server uses the EXISTING state request handler to re-verify Supabase identity, current suspension, current room admission and that member's live connection capability. Invalid, binary, extra-field, oversized, repeated or action messages terminate the socket without any state delivery. Spectator notifications are not implemented; spectator HTTP projections continue to work.

Only after a successful state read does the bridge subscribe to durable owner commit invalidations. It immediately rechecks state after subscribing, so no commit can be lost in the read/subscribe gap. Each peer coalesces notifications and has one read/auth check in flight. Fresh authentication/admission/token checks precede changed notifications and run at each heartbeat even when idle. Invalidation observers run only after successful durable commits, including scheduler/timeouts, and after recovery. Observer exceptions cannot poison a committed hand. No update is emitted for a rejected, duplicate or failed save.

## Presence and cleanup

Default heartbeat is 15 seconds. Native ping/pong detects an unresponsive connection at the following heartbeat (roughly 15–30 seconds plus event-loop/network delay); every heartbeat also revalidates auth/admission. Failed auth/read, excessive buffered output or missing pong terminates the channel. Authentication/read timeout is five seconds. Limits bound open sockets (default 128), total active auth/read checks including timed-out sockets, frame bytes (12288) and outgoing buffer (16384). This is not a per-IP/user rate limiter or a distributed ownership system.

After an authenticated, bound channel closes, trusted server cleanup queues `disconnectConnection` at the owner and persists it. This does not need an expired/revoked user bearer and accepts no user-selected member ID. Cleanup checks the CURRENT capability: an old socket cannot disconnect a replacement. When two sockets use the same capability, the newer bound socket replaces the old observer; its old close does not disconnect the replacement. Close/heartbeat cleanup never changes cards, bets, seats, stacks or action deadlines. A disconnected player remains seated and the existing server timeout chooses check/fold as usual. Failed cleanup saves halt the owner and require operator recovery; no uncommitted snapshot is sent.

A browser channel failure clears rendered private state and stops automatic reads until explicit reconnect. It preserves an uncertain HTTP command and exact action ID. An uncertain HTTP acknowledgement alone keeps the channel alive and new bets blocked until confirmation; late close/message callbacks from an intentionally closed old channel are ignored. No automatic connection-stealing reconnect loop is introduced. Session account changes/unmount clear the client and channel. Bearer refresh inside an already-bound channel is not implemented: expiration closes it and requires explicit reconnect. HTTP-only clients still have no reliable tab-close presence detection; only authenticated subscribed channels get this presence lifecycle.

## Verification

Actual local TCP/WebSocket tests use the real bridge, authenticated request handler, durable owner and browser transport. They cover private-free notification payloads, commit barriers/timeouts, failed saves, old/same-capability replacement, real no-pong termination, current admission revocation, stolen tokens, strict upgrade/frame limits, idle auth deadlines, observer isolation, explicit shutdown, malformed/late browser events and authentication concurrency after timeout. React lifecycle checks cover notification refresh, preserving the channel during lost acknowledgements, exact receipt retry and hiding cards/stopping reads on socket loss. No real user credentials or remote database writes are used.

Live browser verification will require deliberately configured test infrastructure and assigned accounts later. At that point test two browser accounts, immediate action updates, network loss/explicit reconnect, closing the old tab after reconnect and unchanged total chips. Current unconfigured Preview cannot demonstrate live online play. Lobby assignment, production startup/recovery/discovery, spectator push, token renewal and per-user limits remain separate work. Railway remains deferred until development is complete.
