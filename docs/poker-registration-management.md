# Manager configuration and frozen single-table handoff

This connects existing admin/store tournament managers to free intake configuration and **2–6 participant, ONE-table** finalization. It does not create multiple independent tournament winners. Seven or more registrations cannot be finalized until multi-table balancing/consolidation and global tournament accounting exist. Capacity configuration can still describe future larger intake, but the UI and backend explicitly block unsupported finalization. This change deploys nothing.

## Current manager authority and session isolation

The manager component is attached to each saved tournament, respecting the existing store permission grey-out. It loads status only on explicit click (not once per hidden tournament row). Missing service configuration disables it. Configure accepts capacity 2–600 and intake enabled; finalization requires a confirmation of the current registered count. Mutations stop on uncertain results until status reload. A frozen pending plan exposes a resume action for the SAME room, not a new plan. Successful status reports only aggregate policy/count and room ID/count/assignment flag, never participant UUIDs, private checkpoints or cards.

The Next same-origin POST route `/api/poker/registration-management` chooses the existing cookie client via server-owned `tournamentActor(scope)`: admin and store sessions stay separate. Browser bearer headers/cookies are not forwarded. The route obtains the selected verified session's bearer server-side, strips scope and passes only the strict manager command through the fixed configured room-service origin. Changing scope cannot grant a role: the selected session and backend authorization must both pass. No service-role key enters Next client props or browser code.

The separate backend manager handler performs fresh Supabase Auth/suspension verification and calls `poker_registration_manage_allowed(tournament UUID)` with that SAME USER bearer/public key. This is a SECURITY INVOKER boolean RPC, executable by authenticated only, with empty search_path. It checks current non-suspended identity and either current admin rights or ownership of the event's store PLUS enabled tournament-store permission, using existing public-table RLS. No actor/store UUID or user_metadata privilege can be selected by a request. Unknown/wrong managers get no policy data. The handler checks again with fresh Auth and permission immediately before admission binding, after potentially slow checkpoint work. Configure/status also require current authority. Abort before dispatch prevents a mutation; abort after a freeze/save does not undo committed state.

## Immutable frozen plan and provisioning

The sixth prepared migration creates an RLS-protected, backend-only finalization manifest. The freeze RPC locks the tournament row (same lock order as intake/configure/provision), verifies publication, real clock deadline and the expected reviewed participant count, and requires 2–6 exact current entries. It copies their UUID roster, start and structure, chooses one room UUID, derives capacity 2 for two players or 6 otherwise, and pauses intake. Retries return that same immutable plan; a different expected count fails. Private roster data is only returned to the trusted registry, never the manager HTTP response.

Updated intake/configure projections check the manifest too: new registrations, cancellation and policy changes stop as soon as freezing commits, BEFORE an encrypted checkpoint/binding exists. Already-present registration receipt retries remain harmless. The provision RPC now requires intake-managed tournaments to use their exact frozen room, roster, capacity, schedule/structure and no spectators. Other room IDs/subset rosters are refused; tournaments without intake preserve their earlier trusted provisioning path. A real clock check occurs after tournament and pristine-checkpoint locks before insertion, preventing late new binding after waiting. Existing matching bindings can still be reconciled after start/unpublication.

Registry finalization coalesces equal requests for a tournament, rejects a competing reviewed count, and reserves the owner before storage work so no caller can see an unbound in-memory room. It creates the pristine encrypted version-one empty checkpoint, rechecks request authority, then binds the entire manifest roster transactionally through the existing private admissions/provision RPC. Acknowledgement comes only after durable checkpoint + DB binding success. The scheduler is NOT started here; explicitly configured startup/discovery remains necessary.

On retry, a missing checkpoint can be created under the SAME frozen room ID. An existing unbound checkpoint must decrypt and match the frozen configuration, version one, no seats/hand, revision zero and zero hands. It is NOT recovered/saved before binding, because doing so would break the pristine-only SQL rule. After binding, normal disconnected recovery is persisted. Corrupt, changed or nonpristine state fails closed; nothing is deleted/redealt. If the binding already committed but its acknowledgement was lost, the registry validates the existing binding and original expected count/current admission subset, then loads the same saved owner. Current roster deletion does not lower the original required participant count or add replacements.

A frozen plan is not automatically thawed/replaced on Auth deletion, deadline expiry, key/storage problems or schedule/structure edits. Existing public tournament forms can still edit those fields; a pending bind compares against the frozen originals and refuses mismatch. Operators must preserve the original configuration during finalization and reconcile failures explicitly. Changing public schedule/structure after freezing is not a supported repair flow. There is no UI abort/unfreeze or automatic roster replacement, and no claim of distributed leader election: all room requests must route to the same process.

## Explicit composition and remaining work

Node HTTP composition optionally receives `managerHandler: registry.managerHandler({origins,auth})` in addition to the existing player/lobby handlers. The fixed Next gateway origin remains POKER_ROOM_SERVICE_ORIGIN. No new environment is configured. Finalization creates admissions used by the assigned-room lobby; members still explicitly join/reconnect, and the existing scheduler requires the complete original roster connected before first deal. This is free intake only, not paid entry, re-entry, wallet/prize transfer, late entry or table movement.

All SIX backend migrations remain UNAPPLIED to production. No real policies, registrations, plans, room admissions, service process, Railway, production merge or deployment are created by this work. Live QA requires deliberately configured test infrastructure. Next operational work includes startup discovery/scheduler attachment, frozen failure reconciliation tooling, multi-table lifecycle and final approved-demo layout integration.

## Verification

New isolated PostgreSQL suite applies the earlier settings/store-access migrations and all six backend migrations. It checks actual user-context admin/store/revoked/suspended rights, freeze expected-count guards, intake locking before binding, exact roster/room guards, real encrypted registry handoff, pristine orphan reuse, nonpristine refusal, six-person start/chip conservation and preserving the SAME hand after restart/retry. It also checks draft/edited-config refusal, response privacy, invoker flags and browser ACL/RLS. PGlite is a single connection, so this is not cross-session PostgreSQL lock stress QA; competing-session/deadline-wait tests remain required before deployment.

Node tests cover coalescing, conflicting reviewed counts, lost checkpoint/binding acknowledgements, no fresh-deal fallback, authorization loss before bind, corruption/config/roster mismatch, commit barriers, strict manager grammar and actual Supabase user-bearer/public-key context. A separate real Next-route test isolates only cookie actors and proves admin/store session selection, stripped headers/scope, fixed upstream, byte/origin/config/auth failure handling. React lifecycle tests cover configure, confirmation, reviewed count, unconfigured/locked managers, unsupported multi-table counts and exact resume after uncertain results. Existing engine, lobby/intake, WebSocket, DB and UI checks stay in CI.
